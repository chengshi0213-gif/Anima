# v1.2.3 规划 — Harness 骨架工程：打断 · 缓存 · 压缩 · 恢复

> **核心目标**：补齐 Agent 循环本身的工程质量。
> v1.2.1 / v1.2.2 解决"能不能做"（工具广度 + 功能层），
> 本版本解决"做得稳不稳"——这五件事不做，功能做完了用起来还是"不如 Claude Code"。
>
> 版本：`1.2.3`　　分支：`feat/v1.2.3-harness`　　依赖：`>= 1.2.2`
> 主战场：`agent_base.py`（ReAct 循环本体），改的是骨架，不加新功能。

## 一、问题定位（复审 Claude Code 架构的结论）

Claude Code 与 Anima 的差距分三层：

```
功能层（v1.2.1 + v1.2.2 已规划）
  记忆 / 技能 / Plan Mode / 权限 / Diff / 工具集
  → 决定"能不能做"

骨架层（本版本，H 系列）
  打断改道 / 缓存架构 / 结构化压缩 / 文件状态追踪 / 错误恢复 / 上下文经济
  → 决定"做得稳不稳、贵不贵"

行为层（H8，持续迭代无终点）
  判断力提示词：何时问何时做 / 完成标准 / 汇报方式 / 边界感
  → 决定"做得对不对"
```

已验证的现状问题（源码级）：

| 问题 | 位置 | 后果 |
|---|---|---|
| `run()` 循环无 cancel 检查、无消息注入点 | `agent_base.py` | 用户看着 Agent 跑偏只能等它烧完预算 |
| `_compress_history` 每 5 轮改写消息中段 | `agent_compress.py` | 前缀一变 prompt cache 全废，长任务成本翻几倍 |
| 压缩 = 占位符替换 + digest | `agent_compress.py` | 压缩两次后 Agent 基本失忆 |
| `file_edit` 不要求先读过 | `xi_worker.py` | Agent 盲改没读过的文件 |
| `for tc in tool_calls` 串行 await | `agent_base.py` | 三个独立 file_read 排队跑 |
| 无失败模式检测 | `agent_base.py` | Agent 卡在同一个错上反复试 10 轮无保护 |

## 二、H 系列任务

### H1 — 中途打断与改道（P0，体感差距最大）

**目标**：任务运行中，用户随时可以 ① 叫停 ② 插话改方向，下一轮生效。

```python
# agent_base.py：每个运行中的 session 挂一个控制信箱
_steering: dict[str, dict] = {}   # session_id → {"cancel": bool, "messages": [str]}

# run() 循环每轮开头检查：
for turn in range(1, self.max_turns + 1):
    ctl = _steering.get(session_id, {})
    if ctl.get("cancel"):
        # 优雅收尾：让模型用 1 轮总结已做的事 + 已改文件，再返回
        return await self._graceful_stop(messages, files_changed, turn)
    for user_msg in ctl.pop("messages", []):
        # 用户插话 → 作为 user 消息注入，模型下一轮看到并调整方向
        messages.append({"role": "user",
                         "content": f"[用户插话] {user_msg}"})
```

```python
# websocket_server.py：两个新消息类型
# {"type": "steer",  "session_id": ..., "content": "别改那个文件，先跑通测试"}
# {"type": "cancel", "session_id": ...}
```

**前端**：运行中的会话显示「⏸ 插话」输入框 +「⏹ 停止」按钮。
停止不是杀进程——是让 Agent 体面收尾（报告做到哪了、改了什么）。

### H2 — 缓存友好的消息架构（P0，直接省钱）

**原则**：messages 在 run 期间**只追加、不修改**。压缩只在阈值触发，一次到位。

```python
# 改动 1：废除 compress_every=5 的定期压缩
#   触发条件改为：累计字符 > max_total_chars * 0.7（快爆了才压）
#   → 绝大多数任务全程零压缩，前缀始终稳定，
#     DeepSeek/Kimi 的自动前缀缓存全程命中，每轮只为增量付费

# 改动 2：system prompt 稳定化
#   dynamic_prompt（MCP 工具列表等每轮可变的部分）从 system 移到
#   首条 user 消息，或固定快照在 run 开始时取一次——
#   system 内容一变，缓存从第 0 字节失效

# 改动 3：压缩与驱逐对齐（与 H7 联合设计）
#   所有"修改历史"的操作（压缩/大结果驱逐）只发生在同一个压缩事件里
#   → 缓存只断一次，而不是每轮都断
```

**度量**：日志里记录每轮 `prompt_cache_hit_tokens`（DeepSeek 响应里有），
发版前后对比同任务成本，预期长任务降 50%+。

### H3 — 结构化压缩（P0，长任务不失忆）

压缩时不再用占位符，改为一次 LLM 调用生成**八段式摘要**：

```
1. 原始任务（用户最初要什么，逐字保留）
2. 技术决策（选了什么方案、为什么）
3. 已改文件（路径 + 每个文件改了什么，一行一个）
4. 踩过的错（错误信息 + 最终怎么解决的——防止重蹈覆辙）
5. 关键代码片段（正在改的函数签名/接口，原文保留）
6. 用户插话（所有用户中途给的指示，逐条保留）
7. 待办事项（计划里还没做完的步骤）
8. 当前进展（压缩那一刻正在干什么、下一步是什么）
```

```python
# agent_compress.py 重写 _compress_history：
# [system, 八段式摘要(role=user), 最近 N 轮原文] ← 压缩后的新结构
# 摘要生成用便宜模型（deepseek-v4-flash），失败时回退旧占位符逻辑
```

现有 `_coding_digest`（已改文件+关键命令）是第 3、4 段的雏形，升级而非重写。

### H4 — Read-before-Edit 强制 + 文件状态追踪（P0，防盲改）

```python
# agent_base.py：per-run 文件状态表
self._file_state: dict[str, float] = {}   # path → 读取时的 mtime

# _execute_tool 拦截层：
# file_read 成功 → 记录 _file_state[path] = mtime
# file_edit / file_write(已存在文件) 前置检查：
#   path 不在 _file_state → 拒绝：
#     {"error": "先 file_read 读过这个文件再改（防止盲改）"}
#   磁盘 mtime != 记录值 → 拒绝：
#     {"error": "文件在你读过之后被外部修改了，请重新 file_read"}
```

这是**硬闸门**，不是提示词约定——模型偷懒也过不去。
`file_watcher.py` 已存在，后续可升级为主动推送"文件被外部改了"的 system-reminder（P2）。

# agent_base.py：同一轮的多个工具调用，只读工具并行执行
_PARALLEL_SAFE = {"file_read", "list_dir", "search_code", "glob_files",

### H6 — 循环级错误恢复（P1，防呆防卡死）

```python
# agent_base.py 三道保险：

# 1. 重复失败熔断
#   hash(tool_name + json(args)) 连续失败 3 次
#   → 注入提示："这个调用已连续失败 3 次，换一种方法，
#     或者用 ask_user 把情况告诉用户"
#   同一 hash 第 5 次 → 强制停止该工具本轮调用

# 2. API 故障退避
#   429/5xx → 指数退避重试（2s/8s/30s，最多 3 次）
#   重试耗尽 → 走 _FALLBACK_CHAIN 换下一个 provider 续跑
#   （messages 不变，只换模型——比直接报错死掉好得多）

# 3. 输出截断续写
#   finish_reason == "length" 且无 tool_calls
#   → 追加 "继续" 让模型续写，最多续 2 次
```

### H7 — 上下文经济学（P1，与 H2 联合设计）

```python
# 1. 分级工具预算（替代单一 tool_result_cap）
TOOL_BUDGETS = {
    "file_read":   8192,   # 读代码要看得全
    "search_code": 4096,
    "shell_run":   6144,   # 测试输出要看得到错误
    "list_dir":    2048,
    "map_project": 3072,
    "web_search":  3072,
    "_default":    2048,
}

# 2. 压缩点驱逐（不做每轮微压缩——那会天天打破缓存，见 H2 改动 3）
#   压缩事件触发时，摘要之外再做一件事：
#   超过 4KB 的旧工具结果 → 替换为指纹
#   "[file_read E:\...\auth.py 1-600 行，已读，需要时重新读取]"

# 3. system-reminder 轻量注入
#   状态类信息（任务超时预警/确认结果/文件外部变更）
#   以带标记的 user 消息注入："[系统提醒] ..."
#   模型知道这不是用户说话，但能据此调整行为
```

**设计张力（明示）**：Claude Code 的每轮微压缩会持续打破缓存，它靠 cache
breakpoint 机制兜住成本；OpenAI 兼容 API 没有手动断点，所以 Anima 的正确选择是
**驱逐对齐压缩事件**——缓存只断在不得不断的那一次。

### H8 — 行为提示词迭代机制（P1，持续无终点）

这部分没有捷径，建立的是**机制**而不是一次性产出：

```
1. 失败案例库 docs/agent-failure-cases.md
   每条记录：任务 → Agent 做错了什么 → 应该怎么做 → 对应提示词修订
   来源：用户打断（H1 的 cancel/steer 事件自动标记该会话）、
        用户负面反馈、熔断触发（H6）的会话

2. 首批行为规则（参照 Claude Code 行为层，写进 executor 提示词）：
   · 可逆的动作直接做，不可逆的先问（删除/push/发布）
   · 没跑过验证不许说"完成"；失败就说失败，不粉饰
   · 汇报结论先行：第一句话回答"结果是什么"，过程放后面
   · 不做任务范围外的"顺手优化"；不留"我改对了"式的注释
   · 引用代码必须带 文件:行号
   · 卡住超过 3 轮没进展 → 主动 ask_user 而不是硬试

3. 节奏：每个 minor 版本发版前过一遍案例库，把新规则合入提示词
```

## 五、验收标准

### 场景 A：中途改道（H1）
```
Agent 正在重构模块 A，用户发现方向不对，输入插话：
  "停一下方向错了，应该改 B 不是 A"
预期：Agent 下一轮收到插话，停止改 A，转向 B
     已对 A 的改动主动汇报，问用户要不要回滚
```

### 场景 B：成本对比（H2）
```
同一个 30 轮编程任务，v1.2.2 vs v1.2.3 各跑一遍
预期：v1.2.3 的 prompt_cache_hit_tokens 占比 > 60%
     总成本下降 ≥ 50%
```

### 场景 C：压缩后续跑（H3）
```
构造一个触发压缩的长任务（读 10 个大文件 + 改 5 个）
预期：压缩后 Agent 仍记得：改过哪些文件、踩过什么错、下一步是什么
     不重复读已读文件、不重犯已解决的错
```

### 场景 D：盲改拦截（H4）
```
诱导测试：任务描述里直接给出"把 config.py 第 10 行改成 X"
预期：Agent 直接 file_edit → 被闸门拒绝 → 被迫先 file_read → 再改
```

### 场景 E：熔断（H6）
```
构造必败工具调用（不存在的命令）
预期：3 次后 Agent 收到换方法提示；不会卡死烧完 60 轮预算
```
