# v1.3 规划 — 厚 Harness：让弱模型也强（不依赖 Claude）

> **核心命题**：Anima 的输出质量天花板,不应由"租到哪个模型"决定,而应由 harness 决定。
> 目标是把主力模型从 Claude-Sonnet 换成**直连可达的强模型(DeepSeek-V4-Pro 等)**,
> 靠 harness 把模型的不足补回来,测得的自主完成率不显著下降。
>
> 版本:`1.3.0`　　分支:`feat/v1.3-harness-depth`　　依赖:`>= 1.2.3`

---

## 一、命题与证据(2026 年 harness 研究共识)

这一版不是拍脑袋,是有 2026 年研究背书的方向。三个硬数据:

1. **同模型,换 harness,Terminal-Bench 2.0 摆动 30–50 分。** LangChain 把自家 coding agent
   从 52.8% 提到 66.5%,**模型一个字没改**,纯靠 harness。
2. **弱模型 + 强 scaffold 反超强模型 + 弱 scaffold。** Confucius Code Agent 论文:
   Claude-Sonnet + CCA(52.7%) > Claude-Opus + 厂商自带 scaffold(52.0%)。
3. **65% 的企业 agent 失败源于 harness 缺陷**(上下文漂移 / Schema 错位 / 状态退化),
   不是模型推理能力不够。

> 结论:**"做好 harness"是工程上最便宜、杠杆最大的事。** 它正好对齐用户诉求——
> 不接 Claude 也要强输出。

**2026 harness 工程公认的 12 个范畴**(见参考资料 awesome-harness-engineering):
Agent Loop / Planning / Context Compaction / Tool Design / MCP 检索 / Skills /
Permissions / Observability / **Evals** / **Self-Repair** / Multi-Agent / Long-Running。

## 二、现状对照:Anima 已有什么、缺什么

Anima 的 H 系列(v1.2.3)已经命中 Confucius 的两条核心技术(**阈值压缩 H2 + 八段式结构化摘要 H3**),
骨架方向是对的。但对照 12 范畴,补弱模型最关键的几块是空的:

| 范畴 | Anima 现状 | 缺口(对弱模型的影响) |
|---|---|---|
| Agent Loop | ✅ H1/H4/H5/H6 打断·闸门·并行·熔断 | 基本够 |
| Context 压缩 | ✅ H2 阈值 + H3 八段式 | 单阶段;可升级渐进多阶段(Claude Code 是 5 阶段) |
| Planning | ✅ N2 update_plan 计划可见 | 计划只"可见"不"约束执行";缺 Plan-Execute-Verify 分层 |
| **Evals** | ❌ **无**(只有单元测试) | **致命**:改 harness 是盲调,无法证明弱模型够用 |
| **Verify 闸门** | ❌ 只有 H8 提示规则"没验证不许说完成" | **致命**:弱模型最需要"改完自动验证→结构化报错→自修复" |
| **Self-Repair / 失败记忆** | ❌ failure-cases.md 是手填模板 | 弱模型反复踩同一个坑,无跨会话学习 |
| **代码定位/检索** | ⚠️ regex find_symbol,无索引,5000 文件上限 | 大库弱模型找不到正确文件,静默截断 |
| 确定性流水线 | ❌ 只有开放式循环 | 弱模型开放循环易迷路;缺 Agentless 式定位→改→测固定管道 |
| Tool Schema 约束 | ⚠️ 有校验,无解码级 grammar | 弱模型易产出畸形 tool_call |
| Permissions | ✅ D3 四档 + TOOL_SAFETY | 够 |
| Skills | ✅ D2 接线 | 可加负例提升路由(73%→85%) |
| Observability | ✅ M14 hooks + 结构化日志 | 够 |

**一句话**:Anima 有"骨架",缺"反馈闭环 + 度量 + 记忆"——而这三样正是把弱模型抬起来的关键。

## 三、杠杆排序(按"对弱模型 ROI")

研究反复强调:**反馈型信号(带上下文的错误)远胜二元通过/失败**,**度量先于优化**。
据此排序:

```
P0  Eval 脊柱      —— 不能度量就不能调。先有"DeepSeek 当前完成率"这个数。
P0  Verify 闸门     —— 改完自动跑测试/lint,结构化报错回灌,自修复到绿。弱模型第一杠杆。
P0  代码定位层      —— 持久符号索引 + 捅破 5000 上限。大库弱模型的命门。
P1  失败记忆自修复  —— 自动采集失败轨迹,检索"相似旧坑→已知解",止住 thrashing。
P1  Agentless 模式  —— 良定义任务走定位→改→测固定管道,弱模型少迷路。
P1  find_symbol 真AST—— Python ast + tree-sitter,消除 regex 脆弱。
P2  渐进多阶段压缩  —— H3 扩成分级压缩,长任务更稳。
P2  Tool schema 强约束—— 解码级 JSON Schema/grammar(看 relay 支持度)。
```

## 四、任务分解

### Phase E — Eval 脊柱(必须最先做,否则全程盲调)

| 编号 | 任务 | 文件 | 估时 |
|---|---|---|---|
| E1 | `eval/tasks/` 任务集:20 个**你自己仓库的真实任务**(修 bug/加功能/补测试),每个含初始状态 + 验收脚本(pytest 断言或 diff 匹配) | `eval/tasks/*.yaml` | 3h |
| E2 | `eval/runner.py`:对指定模型跑全任务集,隔离工作区(临时 git clone),记录每任务 通过/失败/轮数/token/耗时 | `eval/runner.py` | 3h |
| E3 | `eval/report.py`:输出对比报告(模型 A vs B,harness 改动前后),核心数 = **自主完成率** | `eval/report.py` | 1h |
| E4 | 跑一次基线:**DeepSeek-V4-Pro 当前完成率**(不接 Claude)+ Claude-Sonnet 对照 | — | 0.5h |

> 产出:一张表——"换成 DeepSeek,现在能独立做完几道题"。后面每个 harness 改动都用这张表验真伪。

### Phase V — Plan-Execute-Verify 闸门(弱模型最大杠杆)

| 编号 | 任务 | 文件 | 估时 |
|---|---|---|---|
| V1 | `verify_gate.py`:探测项目验证命令(pytest/npm test/tsc/lint),改动后自动跑 | `verify_gate.py` | 2h |
| V2 | 失败→**结构化错误回灌**:把失败输出(报错+定位行+约束)作为新 user 消息注入,不是二元 pass/fail | `executor_worker.py` | 1.5h |
| V3 | 自修复循环:验证失败自动进入修复轮,上限 N 次(默认 3),仍不绿则 ask_user 并存档 | `executor_worker.py` | 1.5h |
| V4 | 把 H8 的"没验证不许说完成"从**提示规则**升级为**硬闸门**:executor 收尾前必须有一次绿色验证记录,否则状态标 `unverified` | `agent_base.py` | 1h |

> 研究依据:Augment PEV——"phase boundaries with gates",反馈必须是带上下文的错误消息。

### Phase L — 代码定位/检索层(大库命门)

| 编号 | 任务 | 文件 | 估时 |
|---|---|---|---|
| L1 | `code_index.py`:持久符号索引(首次建,文件 mtime 增量更新),捅破 5000 上限 | `code_index.py` | 3h |
| L2 | find_symbol/find_usages 改走索引(命中索引秒回,未命中再扫) | `code_intel.py` | 1.5h |
| L3 | `locate_relevant(task)`:给一句任务描述,返回最相关的 top-K 文件/符号(先关键词+路径打分,后续可挂嵌入) | `code_index.py` | 2h |
| L4 | executor 启动注入:大库时先 `locate_relevant` 给候选,省弱模型前几轮乱翻 | `executor_worker.py` | 1h |

### Phase R — 失败记忆与自修复(止血 thrashing)

| 编号 | 任务 | 文件 | 估时 |
|---|---|---|---|
| R1 | `failure_memory.py`:自动采集失败轨迹(报错签名 + 当时动作 + 最终解),落盘 | `failure_memory.py` | 2h |
| R2 | 相似失败检索:新报错出现时,按签名检索"这个坑以前怎么过的",注入提示 | `failure_memory.py` | 1.5h |
| R3 | 跨会话 hindsight notes:任务结束蒸馏"成功策略 / 失败模式"成 markdown,下次同类任务召回 | `failure_memory.py` | 1.5h |

### Phase D — Agentless 确定性模式(弱模型少迷路)

| 编号 | 任务 | 文件 | 估时 |
|---|---|---|---|
| D1 | `agentless_pipeline.py`:固定三段 定位(locate_relevant)→改(生成 patch)→测(verify_gate),不开放循环 | `agentless_pipeline.py` | 3h |
| D2 | 任务路由:良定义的单点修复走 Agentless,模糊探索走开放循环;executor 自动判定或用户用 `quick:` 前缀强制 | `executor_worker.py` | 1h |

### Phase F — 精修(消除弱模型脆弱点)

| 编号 | 任务 | 文件 | 估时 |
|---|---|---|---|
| F1 | find_symbol 真 AST(Python `ast`,JS/TS tree-sitter,其余回退 regex) | `code_intel.py` | 2.5h |
| F2 | 渐进多阶段压缩:H3 扩成 近→中→远 三档保真度 | `agent_compress.py` | 1.5h |
| F3 | Tool-call schema 强校验 + 畸形自动重试(给弱模型纠错而非直接失败) | `agent_resilience.py` | 1.5h |

**总估时:约 48 小时**(Eval 7.5h / Verify 6h / Localize 7.5h / Repair 5h / Agentless 4h / 精修 5.5h,余量含测试与联调)

## 五、验收标准(用数字,不用感觉)

唯一硬标准:**Phase E 的完成率表,改动前后对比。**

```
验收 1(主目标):DeepSeek-V4-Pro(不接 Claude)在 20 任务集上的自主完成率,
                经 Phase V+L+R 后,相对基线提升 ≥ 15 个百分点。

验收 2(对标目标):DeepSeek-V4-Pro + 厚 harness 的完成率,
                达到 Claude-Sonnet + 当前 harness 的 ≥ 90%。
                (即:把"换便宜模型"的代价压到 10% 以内)

验收 3(稳定性):同一任务跑 3 遍,完成率方差下降(确定性增强)。
```

达不到验收 1 就说明某个 Phase 没真起作用,回去查,而不是继续堆功能。

## 六、边界与风险

- **不追 Claude Code 的全部体量。** 它是多年团队产品(5 阶段压缩 / 27 类钩子 / 子代理重建权限)。
  我们只补"对弱模型 ROI 最高"的那几块,不做全面对标。
- **Eval 任务集的代表性是命门。** 20 个任务必须真实、可自动判分;否则数字会骗人。
  宁可少而真,不可多而水。
- **嵌入式语义检索暂不做**(L3 先用关键词+路径打分)。等关键词版被证明不够再上嵌入,避免过早复杂化。
- **relay 仍保留为可选上档。** 厚 harness 是为了"不依赖"Claude,不是"禁止"——
  用户配了 relay 仍可一键切到 Claude-Sonnet 再上一个台阶。

## 七、执行顺序

```
Week 1：E1→E2→E3→E4(先把度量建起来,拿到 DeepSeek 基线数)
Week 2：V1→V2→V3→V4(Verify 闸门;每做一步回跑 eval 看完成率动没动)
Week 3：L1→L2→L3→L4(定位层;大库任务进 eval 集验证)
Week 4：R1→R2→R3 + D1→D2(失败记忆 + Agentless 模式)
精修：  F1→F2→F3(有余力再做)
收尾：  跑终版 eval,出"DeepSeek vs Claude / 改动前后"完整对比报告 + CHANGELOG + 版本号 1.3.0
```

**纪律延续**:一任务一提交,每次跑全测试套件(637+);新模块独立成文件,不撑爆 agent_base.py 600 红线;
**每个 Phase 做完必须回跑 eval**,用完成率数字证明它真起作用了。
