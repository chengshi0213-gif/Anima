# v1.3 厚 Harness — 执行纪要（第一批落地）

> 规划见 [v1.3-harness-depth-plan.md](v1.3-harness-depth-plan.md)。本文件记录**实际落地**了哪些、怎么用、剩什么。
> 分支 `feat/v1.3-harness-depth`（从 v1.2.3 / 736 测试绿切出）。

## 背景：为什么先做 Verify 闸门

源于一次对 Fable 5（2026-06 发布的 Mythos 级模型）"为什么这么强"的全网复盘。剥开模型本身，
它的工程化优势可拆成三层，其中**对弱模型 ROI 最高、Anima 又恰好缺**的是：

- **执行前交叉验证**——"声称完成"前先用工具结果核对，而不是凭感觉收工；
- **结构化报错回灌**——失败反馈必须是带上下文的错误，不是二元 pass/fail；
- **跨会话记忆**——同一类坑别在不同会话里反复从零踩。

这正对应 v1.3 规划里的 **Phase V（Verify 闸门）** 和 **Phase R（失败记忆）**。本批先把这两块做扎实。

## 已落地

### Phase V — Plan-Execute-Verify 闸门 ✅

把 v1.2.3 H8 的"没验证不许说完成"从**提示规则**升级为**硬闸门**。

**新模块 `backend/verify_gate.py`**（纯函数，35 测试）：
- `detect_verify_command(root)` — 探测项目验证命令：pytest / npm test / tsc / cargo / go
- `looks_like_verify(cmd)` — 判断模型自己跑的某条 shell 是不是"验证"（免重复跑闸门）
- `run_verification(root)` — 子进程跑验证，返回结构化 `{ok, exit_code, kind, failure_summary}`
- `summarize_failure(...)` — 从 pytest FAILED / tsc error / traceback 抠关键错误行
- `format_repair_message(...)` — 把失败结构化成回灌给模型的修复指令

**`backend/agent_base.py` 接入**（默认关，聊天人格零影响）：
- 新增 `self.verify_gate` / `self.max_repair_rounds`（executor 置 `verify_gate=True`）
- 会话级 `verified_green`：改文件 → 置假（旧绿作废）；shell 跑验证且 exit 0 → 置真
- 完成判定处插闸门：改过文件却没绿就声称完成 → `_run_verify_gate` 主动跑验证
  - 绿 → 放行
  - 红 → 结构化报错作为新 user 消息回灌，自修复，最多 `max_repair_rounds`（默认 3）轮
  - 修复额度用尽仍红 → 返回 `status: "unverified"`（不再谎称 completed）
- 验证在 `asyncio.to_thread` 跑，不阻塞事件循环

**效果**：弱模型最容易"改完没测就说好了"，现在被硬闸门接住，强制进入"红→读报错→修→再验证"的闭环。

### Phase R — 跨会话失败记忆 ✅

**新模块 `backend/failure_memory.py`**（13 测试）：
- `error_signature(category, text)` — 把易变细节（路径 / 行号 / pytest 节点名 / 数字 / 十六进制地址）
  归一化后生成稳定签名，**同类错误跨会话命中同签名**
- `FailureMemory` — JSON 落盘（`DATA_DIR/failure_memory.json`）的 签名→频次/摘要 知识库，线程安全
- 接入 Verify 闸门：验证红时先 `recall` 历史、再 `record` 本次；历史命中就把
  "[失败记忆] 这类错误历史上出现过 N 次"附到修复消息，止住弱模型盲目重试同一招

> 诚实边界：本版只记"这类坑反复出现 + 首次摘要"，**不自动记解法**（自动判定解法不可靠，
> 易引噪声）。解法蒸馏（hindsight note）留待后续用 LLM 升级。

### Phase E — 评估脊柱 ✅

把"改 harness 凭感觉"升级为"改 harness 看数字"。核心数永远是**自主完成率**。

**新包 `backend/eval/`**（23 测试，全离线）：
- `spec.py` — 任务集 schema。一道题 = 一个**自包含微工作区**（初始文件 + 提示 + 验收命令），
  声明式 yaml。不 clone 整仓库 → 可复现、跑得快、精确隔离被测点。
- `runner.py` — 隔离临时工作区物化 → 调 solver 让 agent 改 → 跑验收命令评分（**复用
  verify_gate.run_verification**，同一套结构化失败摘要）。**solver 可注入** → 框架本身离线可测；
  `make_executor_solver()` 是真实跑基线用的（驱动 executor，烧 API）。
- `report.py` — 完成率报告 + **改动前后 / 模型 A vs B 对比表**（逐题标"🟢修好了/🔴改坏了"）。
- `tasks/` — 6 道种子题（bug-fix / add-feature / edge-case），每道**初始即红**（有纪律闸门
  `test_seed_task_starts_red` 守着：初始能过的题没判别力，会让基线虚高）。目标扩到 ~20 道。
- `__main__.py` — `python -m eval --model X --label Y` 跑基线（E4）。

**度量与执行解耦**是关键设计：框架（建题/跑/报告）离线可测、随单测一起绿；真正烧 API 额度的
**"跑 DeepSeek 基线"是 CLI 一步，留给用户一键触发**——不替用户擅自花额度（呼应"能省则省"）。

> 可移植坑：任务 verify 用 `{py}` 占位符（runner 替换成 `sys.executable`），
> 避免裸 `python`/`pytest` 依赖 PATH——用户机解释器是 `C:\Python314\python.exe`，
> 裸名解析不到会让全部题误判为红、污染基线。

> **E4 待用户执行**：`python -m eval --model DeepSeek-V4-Pro --label baseline`
> （+ `--model Claude-Sonnet-4.6 --label claude-ref` 对照）。这一步拿到第一张真实完成率表，
> 之后 Verify 闸门的收益就能用 `format_compare` 量化出来。

### 架构债：拆 `agent_base.py` 工具咽喉 → `agent_tools.py` ✅

Phase V/R 落地后 `agent_base.py` 涨到 694 行，超 600 软红线。真问题是"工具执行咽喉"
那坨（`_execute_tool` / `_guard_tool` / `_post_tool` / `_file_gate`，~95 行核心路径）
和 ReAct 主循环挤在一个文件。按既有 Mixin 分层惯例（compress / logging / resilience）
把它抽成 **`backend/agent_tools.py` 的 `AgentToolGateMixin`**：

- 四个咽喉方法整体平移，零逻辑改动（纯搬家）
- `PermissionRequest` 异常类一并迁入（工具/权限语义同源，且让新模块零依赖 agent_base → 无循环 import）
- `agent_base.py` 改 `from agent_tools import AgentToolGateMixin, PermissionRequest` 并 re-export，
  外部 5 处 `from agent_base import PermissionRequest`（computer_tools / websearch / ws_manager /
  xi_worker / 测试）**全部不受影响**，跨模块 `isinstance` / `except` 身份一致
- `agent_base.py` **694 → 546 行**，回到软红线内；职责更聚焦（只剩模型路由 + ReAct 循环 + 压缩/humanize 钩子）

契约已被现有套件实测：`test_engine_core.py` 直接 `from agent_base import PermissionRequest`，
工具咽喉被 test_async_dispatch / test_engine_core / test_hooks / test_mcp_client 覆盖，全绿。
