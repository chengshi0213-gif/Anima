# Anima v1.2.0 — 工程纪律与架构规范（防屎山）

**日期**: 2026-06-07 · **适用**: v1.2.0 全部里程碑（M11–M16 / D1–D3 / W1–W2）
**配套**: `v1.2.0-design.md`（工程实现）· `v1.2.0-productivity-strategy.md`（战略）· `anima-design-system.md`（设计）· `WORKFLOW.md`（三方协作）

---

## 〇、一句话

> v1.2.0 同时上四支柱，最大风险**不是功能做不出，是代码失控变屎山**。
> 本文是**硬约束**，不是建议。每个改动开工前先对照第七节红线清单。

核心信条：**只增不改 · 积木化 · 单一咽喉 · 测试先行 · 小步可回滚。**

## 一、架构北极星：积木化，不是堆砌

Anima 后端已有一套优雅的可扩展骨架，**v1.2.0 必须顺着它长，而不是另起炉灶**：

### 1.1 能力积木协议（`capabilities.py` = 命脉）
每个新能力 = 一块 `Capability`（贡献 `tool_defs` + `dispatch` + `prompt_fragment`），注册进 `_FACTORIES`，在 worker 的 `CAPS` 列表加一个字符串。
- MCP、Git、TDD —— **全部是加积木，不是改核心**。
- 现有 4 块积木（execution/web/divination/orchestration）+ 13 个工具 **字节级不动**。

### 1.2 只增不改（Additive-Only）
- 新功能走新文件 / 新积木 / 新配置命名空间（`mcp:`/`sandbox:`/`hooks:`），默认关。
- 老 `config.yaml`、老前端、194 个测试**必须照常工作**。
- 唯一允许动核心的地方：三个内核改动（见 design.md 第三节），每个都有 `iscoroutine` 守卫 + 单一调用点 + 新回归测试三重兜底。

### 1.3 单一咽喉（Single Choke Point）
- 所有工具调用经 `agent_base.py:_execute_tool`（全局唯一调用点）。
- MCP 异步化、权限确认、Hooks —— **全挂这一个点**，不要散落到各处。
- 好处：一处加守卫，全局生效；审计/日志/确认天然集中。

### 1.4 后端分层与依赖方向（不许逆流）
```
routes/*.py      (HTTP 边界，自注册 register(app))
   │ 只调 ↓
worker (xi_worker / 子员工)   ← 装配 capabilities
   │ 只调 ↓
capabilities.py  (积木注册表)
   │ 只调 ↓
工具实现 (git_tools / mcp_client / test_runner / websearch …)
   │ 只调 ↓
基础设施 (config / memory_* / ws_manager / notifier / logger)
```
**规则**：上层可依赖下层，**下层绝不 import 上层**。基础设施不 import 业务。违反=屎山起点。

## 二、模块边界与文件大小红线

### 2.1 现状体检
- **后端（17.5K 行，健康）**：最大 `skill_manager.py`(1232)、`community_skills.py`(897)、`agent_base.py`(661)。模块边界清晰，继续保持。
- **前端（11.9K 行，屎山高危区）**：`styles.css`(3941)、`settings.js`(1668)、`workflow.js`(1601)、`index.html`(1496) —— **四个巨型单文件，v1.2.0 重点治理对象。**

### 2.2 文件大小红线
| 类型 | 软上限（警告） | 硬上限（必须拆） |
|---|---|---|
| 后端 .py | 400 行 | 600 行 |
| 前端 .js | 400 行 | 600 行 |
| .css（token 化后单层） | 500 行 | 800 行 |
| 单个函数 | 50 行 | 80 行 |

- 现存超标文件**不要求立刻全拆**（避免大爆破），但**触碰到就顺手拆**，且**新代码不许再往里堆**。
- 新功能优先开新文件，而非塞进已超标的巨型文件。

### 2.3 新增 vs 改造的判断
- 能用"加积木"解决的，**永远不改老积木**。
- 必须改老文件时：先问"这是 bug 修复还是加功能？"——加功能=另起文件/积木；bug 修复=最小改动 + 补回归测试。

## 三、前端去屎山专项（最大风险区，对接设计 D1–D3）

四个巨型文件的治理计划（**与 `anima-design-system.md` 的 D1/D2/D3 同步推进，不另开战线**）：

| 文件 | 问题 | 治理 | 阶段 |
|---|---|---|---|
| `styles.css` 3941 | 全站样式 + token 混杂单文件 | 抽 `tokens.css`，逐区域拆 `base/components/<模块>.css` | D1→D3 |
| `index.html` 1496 | 巨型 HTML + 内联模板字符串 | 按视图拆模板；动态 HTML 收敛到组件渲染函数 | D2→D3 |
| `settings.js` 1668 | 设置项全堆一处 | 按设置分类拆模块（API/外观/工作流/高级） | D3 |
| `workflow.js` 1601 | 画布+引擎+UI 混在一起 | 拆 `workflow-canvas` / `workflow-engine` / `workflow-ui` | W1 |

**前端硬规则**：
1. 已用 ES modules（`import`），保持——禁止再写全局函数污染。
2. **禁止新增巨型内联 HTML 字符串**（现 `index.html`/`workflow.js` 的反面教材）；动态 UI 走渲染函数 + 模板。
3. 样式只用语义 token（见 design-system 第二节），禁止散落魔法值（`#fff`/`14px` 硬编码）。
4. 一个 .js 文件 = 一个清晰职责；超 400 行先想拆。

## 四、开发流程：每个改动怎么走

### 4.1 标准节拍（每个里程碑/功能）
```
1. 设计   → 对照 design.md，确认是"加积木"还是"动内核"；动内核要格外慎重
2. 测试先行 → 先写/改回归测试与新测试，明确"做完长什么样"
3. 实现   → 小步提交，每步可独立回滚；遵守文件大小红线
4. 验证   → 跑全量测试 + 该模块 smoke；内核改动必跑 4 个回归哨兵
5. 提交   → 语义化 commit message；不夹带无关改动(如 WORKFLOW.md 别人的笔记)
```

### 4.2 三方协作分工（见 `WORKFLOW.md`）
- **Claude（本会话）**：规划/架构判断/写提示词/评审/跨会话记忆。
- **Codex** `codex exec -s workspace-write`：读代码→改文件→跑测试→提交（功能实现/重构/多文件编辑）。
- **Hermes** `hermes -z`：调研/文档/长任务/联网。
- 约束写法：给 Codex 的提示词若说"不改 X"，必须同时写清例外，否则它会严格遵守导致合理改动被拒。

### 4.3 内核改动的特殊流程（M11 内核 1/2/3）
内核改动牵一发动全身，**强制流程**：
1. 先写"向后兼容回归测试"（如 `test_async_dispatch.py`：同步工具走 async 路径结果不变）。
2. 改单一调用点 + 加守卫（`iscoroutine`）。
3. 跑全量 194 + 新测试，全绿才算数。
4. 子员工/orchestrator 透明继承，不单独改。

### 4.4 Definition of Done（一个改动"完成"的定义）
- [ ] 功能可用 + 有对应测试，全量测试绿（含 4 个回归哨兵）
- [ ] 不超文件大小硬红线（或已顺手拆）
- [ ] 无新增魔法值/全局污染/巨型内联 HTML
- [ ] 配置项默认关、向后兼容
- [ ] commit 干净（无夹带）、message 语义化
- [ ] 涉及发版的，过 `RELEASING.md` 的 smoke test

## 五、测试策略

### 5.1 测试金字塔
- **单元**（多数）：每个工具/积木/引擎函数。
- **集成**：worker 装配 + 工具分发 + WS 往返。
- **回归哨兵**（不许红）：`test_single_key` / `test_orchestrator` / `test_persona` / `test_git_safety`——每次改动后必过。
- **冒烟**（发版前）：见 `RELEASING.md`（重建 sidecar→`/health`→`DELETE /sessions`→查无 CRITICAL/Traceback）。

### 5.2 每里程碑配独立测试文件
- M11→`test_mcp_client.py`（本地 echo server 测连接/调用/命名空间/容错）
- M12→`test_task_registry.py`（任务状态机/重连 attach）
- M13→`test_git_tools.py` + `test_project_map.py` + `test_test_runner.py`
- M14→`test_confirm.py` + `test_hooks.py`
- **原则**：新功能不许"裸奔上线"；测试和功能同一个 PR。

### 5.3 TDD 循环（支柱② 的 test_runner，也用于自身开发）
- `detect_test_command`（pytest/jest/go test/cargo）+ `run_tests` 解析通过/失败。
- executor 的"改→测→修→绿"循环，开发 Anima 自己时同样适用。

### 5.4 向后兼容是测试的一等公民
- 任何内核/积木改动，必须有"老行为不变"的断言测试。
- 命名空间隔离（`mcp__`前缀）要有"只换 MCP 子集、不碰原生 13 工具"的测试。

## 六、优化规范（别过早优化，也别不优化）

### 6.1 顺序：先正确 → 再清晰 → 最后快
- 不要在功能没稳之前调性能。**过早优化是屎山的另一种来源。**
- 优化前先测量（用已有的结构化日志/崩溃上报定位真瓶颈），别拍脑袋。

### 6.2 Token 经济（直接关系成本，用户反复强调省资源）
- **子员工预算护栏**（深度 2 / 预算 16）是硬上限，新并行能力（delegate_parallel/动态工作流）**复用它，不许绕过**。
- 动态工作流规模量力而行：几十级并行，非 Claude 的上百/上千级（本地中国模型 + 学生算力跑不动也不需要）。
- 上下文压缩（已有 compress）逐步智能化；长会话主动 compact。
- 优先复用已有 token（提示词缓存思路），避免重复灌大上下文。

### 6.3 性能预算（给体验定线）
- 启动：sidecar 就绪 < 既有基线（auto-restart 守护已在）。
- 响应：流式首 token 尽快出（"看着她写"的感知 > 总时长）。
- 内存：PyInstaller 产物体积/常驻内存留意，别让积木无脑膨胀。

### 6.4 可观测性（已有地基，继续用）
- 后端中央结构化日志（task #3 已完成）、本地崩溃上报（task #5）——新模块接入它们，不要各写各的 print。

## 七、防屎山红线清单（开工前对照）

**DO ✅**
- 加积木（新 Capability / 新文件 / 新配置命名空间，默认关）
- 工具逻辑挂单一咽喉 `_execute_tool`
- 测试先行，回归哨兵常绿
- 小步提交、可回滚、commit 干净
- 样式只用语义 token；UI 走渲染函数

**DON'T ❌**
- 改老积木/老工具的签名（除非三重兜底的内核改动）
- 下层 import 上层（依赖逆流）
- 往已超 600 行的文件继续堆代码
- 新增巨型内联 HTML 字符串 / 散落魔法值 / 全局函数污染
- 绕过子员工预算护栏搞无限并行
- 功能不带测试就上
- commit 夹带无关改动（如别人的 `WORKFLOW.md` 笔记）
- 把签名私钥/密钥写进任何入库文件（`tmp_sign/` 已 ignore）

## 八、每里程碑工程检查点（Gate）

每个里程碑收尾前，必须过这道 Gate 才算"完成"：

| Gate | 检查 |
|---|---|
| G1 兼容 | 194 测试 + 4 哨兵全绿；老前端/老配置照常 |
| G2 边界 | 无依赖逆流；新文件不超红线；改动属"加积木"或合规内核改动 |
| G3 测试 | 本里程碑独立测试文件存在且覆盖核心路径 |
| G4 设计 | 涉及 UI 的，用语义 token，对接 design-system 区域计划 |
| G5 成本 | 并行/上下文不绕预算护栏；无明显 token 浪费 |
| G6 发版 | 若发版，过 RELEASING.md smoke test + 版本号三处一致 |
